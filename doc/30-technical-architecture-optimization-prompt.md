# 心理测评系统技术架构优化 Prompt

## 使用说明

将下面代码块中的内容完整复制给 Codex、GitHub Copilot 或其他代码代理，用于从工程质量、架构可维护性、数据库治理、性能、可靠性、测试和交付能力等技术角度全面审查并优化当前工程。

本 Prompt 不要求无理由重写系统，也不以更换 ORM 或框架作为目标。所有优化必须基于当前代码和运行证据，分阶段实施，并保持现有业务闭环、多租户安全和中日英三语能力。

```text
请从技术架构和工程质量角度，全面审查并优化当前心理测评系统。

工程包含：

- Kotlin、Spring Boot、JDBC、PostgreSQL、Redis 后端
- React、TypeScript、Ant Design、React Query、ECharts Web 前端
- Kotlin、Jetpack Compose Android 被测者端
- 独立 auth-starter 认证模块
- PostgreSQL 初始化脚本、GitHub Actions CI 和现有测试

目标不是为了“技术先进”而重写，也不是简单更换 MyBatis、JPA 或其他框架，而是在不破坏现有业务和接口契约的前提下，提高：

- 可维护性
- 数据一致性
- 多租户安全性
- 并发正确性
- 性能和容量
- 可测试性
- 可观测性
- 构建可复现性
- 部署和回滚能力
- 故障恢复能力

一、实施原则

必须遵守：

1. 先审查、测量和输出证据，再决定是否修改。
2. 不允许只根据文件名、类名或已有接口判断功能完善。
3. 不允许为了使用某个框架进行全量重写。
4. 优先渐进式重构，每一步都必须可编译、可测试、可回滚。
5. 保持现有 API 兼容，确需破坏性修改时必须提供版本化迁移方案。
6. 保持现有 PostgreSQL 数据，不能删除或重建用户本地数据库。
7. 不允许使用 H2 测试结果代替 PostgreSQL 行为验证。
8. 多租户条件、对象所有权和业务状态检查不能被 ORM 或全局过滤器隐藏。
9. 不允许降低现有中日英三语、多租户、匿名隐私、审计和幂等能力。
10. 不允许把性能优化建立在猜测上，必须保留优化前后的测量数据。

二、先输出当前技术基线

扫描整个工程并输出以下矩阵：

| 模块 | 技术栈 | 规模 | 主要职责 | 当前风险 | 建议 | 优先级 |
|---|---|---:|---|---|---|---|

至少统计：

- Kotlin、TypeScript、TSX、Android Kotlin 文件数量和代码行数
- 超过 500、800、1000 行的类和页面
- Controller、Service、Repository、Worker 数量
- SQL 数量和 PostgreSQL 专属 SQL 数量
- 单元测试、集成测试、组件测试、E2E 测试数量
- 前端各构建 chunk 原始大小和 gzip 大小
- Android 模块、Screen、ViewModel 和本地存储实现
- 数据库表、索引、唯一约束、外键和检查约束
- 定时任务、异步任务、重试任务和锁实现
- 外部依赖、相邻仓库依赖和构建时下载项
- Actuator、指标、日志、trace 和告警覆盖情况

列出 P0、P1、P2 问题，每个问题必须包含：

- 代码或配置证据
- 影响范围
- 触发条件
- 是否已经通过运行验证
- 推荐修复方案
- 修改风险
- 回滚方式

完成基线后，按优先级直接实施安全、可验证的优化。

三、数据库迁移和数据治理

重点审查当前单一 schema 初始化脚本和手工执行方式。

实现或完善：

1. 引入 Flyway 等版本化迁移机制。
2. 对已经存在数据的 PostgreSQL 数据库制定明确 baseline，不允许自动误判或清空数据库。
3. 当前完整结构作为受控基线，后续每次修改使用不可变的版本脚本。
4. 禁止修改已经在任何环境执行过的迁移文件。
5. CI 必须从空 PostgreSQL 数据库执行全部迁移。
6. CI 还必须从基线结构执行增量迁移，验证升级路径。
7. 对新增非空列、唯一索引和外键提供历史数据预检查及回填步骤。
8. 大表索引和约束变更评估锁表时间，必要时使用 PostgreSQL 并发索引或分阶段迁移。
9. 关键业务状态增加 CHECK 约束或等价数据约束。
10. 为幂等提交、预约、咨询记录、导出任务等补充必要唯一约束。
11. 输出迁移清单、数据影响、执行顺序、回滚和备份要求。

不得把 `spring.sql.init` 重复执行当作正式生产迁移方案。

四、后端代码结构

重点检查超大 Service 和 Repository，例如量表、答卷、统计、导出、通知、任务等模块。

优化目标：

- Controller 只负责协议转换、校验和授权入口
- Application Service 负责编排和事务边界
- Domain Policy 负责评分、状态转换、权限范围和业务规则
- Repository 只负责持久化和查询
- Renderer 负责 PDF、Word、Excel、CSV 等文件生成
- Worker 负责异步领取、重试、超时恢复和状态落库

实施要求：

1. 将超过合理复杂度的类按职责拆分，禁止只是机械拆文件。
2. 把重复 SQL 参数、RowMapper 和分页逻辑提取成明确组件。
3. 读写复杂度高的模块可拆分 Command Repository 与 Query Repository。
4. 所有事务边界必须明确，避免在长事务中执行网络、邮件、Push 或文件上传。
5. 状态流转使用明确的状态机或 Transition Policy，禁止各 Service 自由写状态字符串。
6. 异常统一使用稳定错误码和三语消息，不向用户暴露数据库异常文本。
7. 时间必须明确时区和 Clock 来源，关键时间边界测试不能直接依赖系统当前时间。
8. 对批量写入、批量通知和统计查询避免逐条数据库访问。

五、JDBC、MyBatis、JPA 和查询技术选择

不要默认进行 ORM 迁移。

先分别统计：

- 标准 CRUD 查询
- 动态条件查询
- PostgreSQL 专属查询
- 聚合、窗口函数和报表查询
- 行锁、条件更新和批量写入

然后按以下原则决定：

1. 复杂统计、多租户过滤、行锁和批量写入继续保留显式 SQL。
2. 如果主要问题是参数和结果映射样板代码，可局部试点 MyBatis。
3. 如果需要复杂 SQL 的类型安全和编译期校验，可评估 jOOQ。
4. 只有标准实体 CRUD 占绝对多数时才考虑 JPA。
5. 不允许同时无边界混用 JDBC、MyBatis、JPA 三套持久化方案。
6. 任何试点必须选择一个低风险模块，并比较代码量、性能、可测试性和租户安全。
7. 未证明收益前，不允许全量替换现有 Repository。

输出技术选型 ADR，记录采用、拒绝和暂缓的原因。

六、PostgreSQL 查询和性能

建立真实性能基线，至少覆盖：

- 任务列表
- 答卷保存与提交
- 自动评分
- 预警列表与超时升级
- 群体统计
- 多次测评趋势
- 导出任务查询
- 通知运维查询
- 预约排班和配额检查

要求：

1. 使用真实规模的脱敏或合成数据。
2. 记录 p50、p95、p99、吞吐量和数据库连接使用情况。
3. 对慢查询执行 `EXPLAIN (ANALYZE, BUFFERS)`。
4. 结合 `pg_stat_statements` 判断索引，而不是只凭字段经验添加索引。
5. 检查复合索引字段顺序和租户字段位置。
6. 大数据分页优先评估 keyset pagination，避免深度 offset。
7. 检查 N+1 查询、循环查询和重复加载。
8. 批量任务需要限制批次大小和内存占用。
9. 导出大文件使用流式写入或外部存储，避免全部驻留 JVM 内存。
10. 优化前后保存相同 Case 的对比报告。

七、异步任务、事件和可靠性

检查答卷提交、报告生成、预警、通知、审计、邮件、Push、导出之间的一致性。

建议实现 Transactional Outbox 或等价机制：

1. 业务数据与待发送事件在同一数据库事务落库。
2. Worker 使用幂等键领取事件。
3. 支持重试次数、下一次重试时间、指数退避和最大重试限制。
4. 超过限制进入死信状态，提供运维查询和人工重放。
5. Worker 崩溃后可重新领取超时任务。
6. 多实例并发领取不能重复执行。
7. 外部调用必须配置连接、读取和整体超时。
8. 失败信息需要脱敏，不能保存 Token、密码或敏感答卷内容。
9. 指标至少包含队列长度、处理延迟、成功率、失败率和死信数量。

不要在数据库事务中直接等待邮件、FCM、微信或对象存储响应。

八、API 合同和客户端生成

将 OpenAPI 从草稿升级为可执行合同：

1. 后端接口、错误码、分页、日期格式、枚举和鉴权方式全部进入 OpenAPI。
2. CI 校验 OpenAPI 与 Controller 一致性。
3. 对破坏性 API 变更执行兼容性检查。
4. 自动生成 TypeScript Web Client 和 Kotlin Android Client，或至少生成共享 DTO 类型。
5. 禁止 Web、Android 和后端分别手工维护同一枚举而没有一致性测试。
6. 所有错误响应具有稳定 code、message、traceId 和字段级校验明细。
7. 生成代码与人工业务封装分层，禁止直接修改生成文件。

九、Web 前端工程优化

保持 React、TypeScript、Ant Design、React Query 和 ECharts。

重点优化：

1. 将超大 Page 拆分为页面容器、业务 Hook、表格、表单、弹窗和状态组件。
2. API 请求、缓存 key、错误转换和下载逻辑集中在 feature API 层。
3. React Query 明确 staleTime、retry、失效和乐观更新策略。
4. 页面卸载或筛选变化时取消无效请求。
5. ECharts 按需引入并延迟加载图表模块。
6. 大页面按路由和功能分块，限制主 chunk 和图表 chunk 大小。
7. 图片使用合适尺寸、格式和压缩策略。
8. 国际化资源按领域拆分命名空间，保持三语 key 和占位符一致。
9. 建立类型安全的翻译 key，禁止静默回退到 key。
10. 增加 ESLint、格式检查、未使用代码和循环依赖检测。
11. 保持键盘操作、焦点、颜色对比度和移动端可用性。

构建输出必须记录优化前后 chunk 大小和加载性能。

十、Android 架构优化

保持 Kotlin、Jetpack Compose 和现有 API。

目标结构：

- feature/auth
- feature/tasks
- feature/reports
- feature/appointments
- feature/notifications
- core/network
- core/storage
- core/i18n
- core/designsystem

要求：

1. Screen 不直接承担全部请求、状态、校验和导航逻辑。
2. 使用 ViewModel + StateFlow/不可变 UI State 管理页面状态。
3. 进程重建和旋转后恢复必要状态。
4. Token 和敏感草稿继续加密保存。
5. 普通缓存、离线草稿和待重试动作根据需要使用 Room/DataStore。
6. 网络重试、离线同步和后台上传使用 WorkManager 或等价机制。
7. 应用内语言选择持久化，并向后端发送 `Accept-Language`。
8. 三语文案全部进入 Android resources，禁止恢复内联三语函数。
9. Android 构建工具版本必须符合官方兼容矩阵并在 CI 固定。
10. 增加 ViewModel、Repository、资源合同和关键 Compose UI 测试。

十一、测试体系

建立分层测试：

1. Domain 单元测试：评分、任务时间、状态机、匿名规则、权限策略。
2. Repository PostgreSQL 测试：真实 PostgreSQL，不用 H2 替代关键 SQL。
3. Service 集成测试：事务、幂等、并发、重试、状态日志和审计。
4. Controller 安全测试：角色、租户、对象所有者和越权 ID。
5. Web 组件测试：加载、空数据、失败恢复、权限和关键表单。
6. Playwright E2E：登录、任务、答卷、报告、预警、干预、预约、导出。
7. Android 测试：资源一致性、ViewModel、网络错误、语言切换和深链。
8. 数据库迁移测试：空库安装和历史版本升级。
9. 性能测试：统计、批量通知和并发提交。

必须覆盖：

- 不同租户访问相同 ID
- 匿名测评不能进入个人链路
- 重复提交和并发提交
- 预约配额并发竞争
- Worker 重复领取和宕机恢复
- 通知失败重试和死信
- 导出权限和过期文件
- 中文、日语、英语完整流程

为核心模块设置合理覆盖率门禁，但不能以行覆盖率替代业务 Case。

十二、可观测性和运维

实现：

1. 所有请求生成或透传 traceId/correlationId。
2. 使用结构化 JSON 日志。
3. 日志脱敏 Token、密码、邮箱、手机号、答卷和报告内容。
4. 暴露 Prometheus 指标并建立仪表盘。
5. 记录 HTTP 延迟、错误率、数据库连接、慢查询、Redis、队列积压和 Worker 结果。
6. 为预警延迟、通知失败、导出失败、任务积压和数据库连接耗尽设置告警。
7. 区分 liveness、readiness 和业务依赖健康。
8. 支持优雅停机，停止接单后等待受控任务结束。
9. 制定数据库备份、恢复演练和导出文件生命周期策略。

十三、安全和供应链

检查：

- 默认密钥和开发配置是否可能进入生产
- 日志是否泄露敏感字段
- 上传文件类型、大小和内容限制
- SSRF、路径穿越、公式注入和 CSV 注入
- 邮件、Push、对象存储和 SSO 超时
- Web CSP、XSS、CSRF 和开放重定向
- 依赖漏洞、许可证和 SBOM
- GitHub Actions 第三方 Action 固定版本
- Gradle 依赖验证和 npm lockfile 一致性
- auth-starter 的版本和来源是否可复现

生产环境必须使用 Secret Manager、环境注入或等价安全方案，不能依赖仓库中的默认值。

十四、CI/CD 和构建门禁

CI 至少包含：

- 后端编译和全部测试
- PostgreSQL 空库迁移及升级迁移
- PostgreSQL Repository 集成测试
- Web 测试、TypeScript 构建、lint 和依赖审计
- Web bundle 大小预算
- Android lint、单测和 Debug 构建
- 三语资源一致性测试
- OpenAPI 合同检查
- 覆盖率门禁
- SBOM、SAST 和依赖漏洞扫描
- `git diff --check` 或等价格式检查

构建产物必须可追踪到 commit、依赖版本、数据库 schema 版本和构建时间。

十五、分阶段实施顺序

建议按以下顺序实施，不要一次性大爆炸重构：

阶段 1：安全基线

- 建立技术矩阵和性能基线
- 修复构建工具不兼容
- 固定 auth-starter 版本
- 引入 Flyway baseline
- 增加 PostgreSQL 迁移测试

阶段 2：关键可靠性

- 补充数据库约束
- 完善并发、幂等和行锁测试
- 引入 Outbox 和死信机制
- 增加 trace、指标和告警

阶段 3：代码结构

- 拆分超大 Service 和 Repository
- 拆分 Web 超大 Page
- 拆分 Android Screen，并引入 ViewModel
- 正式化 OpenAPI 并生成客户端

阶段 4：性能和体验

- 优化慢 SQL和分页
- 前端拆包与图表按需加载
- 大导出流式处理
- Android 离线恢复和后台重试

每个阶段必须独立提交、独立验证、可单独回滚。

十六、验证要求

修改完成后必须执行并报告：

- 后端全部单元测试数量和结果
- PostgreSQL 集成测试数量和结果
- 数据库空库迁移和升级迁移结果
- Web 全部测试和生产构建结果
- Web chunk 大小变化
- npm 依赖审计结果
- Android lint、单测和 Debug 构建结果
- 中日英资源一致性测试
- 浏览器 E2E 结果
- 并发、幂等、多租户、匿名隐私和 Worker 恢复测试
- `git diff --check`

如果本机缺少 Android SDK、浏览器、Redis、邮件、FCM 或对象存储等环境，必须明确标记“未验证”，不能把静态检查或 CI 配置视为已通过。

十七、交付格式

开始实施前输出：

1. 当前技术架构图。
2. 模块和规模矩阵。
3. P0/P1/P2 问题清单。
4. 数据库迁移影响。
5. 技术选型 ADR。
6. 分阶段实施计划。
7. 测试和回滚计划。

完成后输出：

1. 实际修改文件。
2. 每项修改解决的问题和证据。
3. 数据库 schema 版本及迁移结果。
4. 测试、构建、性能和安全扫描结果。
5. 尚未验证的项目及原因。
6. 剩余技术债和风险。
7. 当前是否达到：
   - 可开发
   - 可验收
   - 可部署
   - 可上线

四个级别必须分别判断，不能用“测试通过”直接等同于“可上线”。
```

## 建议优先级

首次使用本 Prompt 时，建议先完成以下五项：

1. PostgreSQL 版本化迁移和现有数据库 baseline。
2. PostgreSQL Testcontainers 集成测试。
3. auth-starter 依赖版本固定。
4. 超大后端类、Web 页面和 Android Screen 的职责拆分计划。
5. OpenAPI、Outbox、可观测性和 CI 门禁设计。
