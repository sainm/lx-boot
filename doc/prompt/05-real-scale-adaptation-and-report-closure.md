# 目标：真实量表适配与结果/报表闭环

## 目标

基于当前 `lx-boot` 的真实代码、PostgreSQL 和现有测试，选择一份已经获得授权的真实心理量表，完成从量表导入到结果展示和报表导出的完整闭环：

`量表资料 -> ScalePackage -> 三语校验 -> Golden Case -> 双审批 -> 发布 -> 任务锁定量表版本 -> 答卷提交 -> 计分 -> 结果解释 -> 风险/预警 -> Web 展示 -> Word/PDF/文本报表`

量表必须能够使用自己的计分规则、结果区间、结果解释、建议、维度、常模和风险规则；不能把所有量表都退化成简单求和，也不能把技术 fixture 伪装成正式临床量表。

当前已具备的技术基础：

- ScalePackage 导入、预览、确认、版本冻结和双审批。
- `SIMPLE_SUM`、`REVERSE_SUM`、`WEIGHTED_SUM`、`AVERAGE`、`WEIGHTED_AVERAGE`。
- 缺失策略、作答质量、Z/T 常模治理和 V23 `scoring_trace_json`。
- `report_template` 受控模板：`DEFAULT_SCREENING`、`SINGLE_SCORE`、`DIMENSION_PROFILE`、`NORMATIVE_PROFILE`、`RISK_TRIAGE`。
- Web、Word、PDF、文本报表按模板输出，中日英结果解释和建议留痕。
- PostgreSQL、Web 测试和核心 Playwright E2E 已有技术基线。

当前正式量表清单为空；`E2E_CORE_TECH_FIXTURE`、`SCL90_TECH_DEMO` 只能作为技术验证数据。

本轮收到的 SCL-90 资料已固化为 [SCL-90 source package](/Users/sainm/work/github/lx-boot/doc/scale-packages/scl90-v1-source-draft.json)：90 题、10 个维度、三语草稿、0–4 主计分口径、`SCL90_PROFILE` 受限算法、GSI/PST/PSDI、15/63 号安全规则和 Golden Case。来源包另记录了 14 条互联网参考资料（翻译适配、中文题目措辞、跨语言信效度、常模、版权和自杀风险处置），但它仍是 `DRAFT/BLOCKED_EXTERNAL`，不能替代授权、正式常模或专业审核。

## 可直接执行的 Prompt

```text
请在当前 lx-boot 工程中，完成“一份真实授权心理量表”的适配和结果/报表闭环。

一、范围

只处理 Kotlin/Spring Boot/PostgreSQL 后端、React/TypeScript Web、量表 ScalePackage、评分、结果展示、报表导出和真实 PostgreSQL/E2E 验证。

本轮不得修改 android-app，不安装或配置 Android SDK，不扩展与量表闭环无关的性能、基础设施或框架迁移工作。

二、强制原则

1. 先扫描真实代码、数据库结构、现有迁移和测试，再修改。
2. 不删除、重建、清空或自动迁移用户已有 PostgreSQL 数据。
3. 不修改已经执行过的 Flyway 迁移；新增数据库变化只能创建新的不可变版本。
4. 保持现有 API、历史结果、多租户、匿名隐私、审计和中日英能力。
5. 不把技术 fixture 当成正式量表，不猜测版权、常模、阈值或临床解释。
6. 缺少正式手册、授权、常模或专业审核时，必须停止正式发布并标记为 `BLOCKED_EXTERNAL` 或 `NEEDS_REVIEW`。
7. 不允许用任意脚本访问数据库、文件或网络来实现计分；不支持的算法必须阻止发布。
8. 每一步都必须可编译、可测试、可回滚；不得只修改文档宣称完成。

三、先确认真实量表输入

要求业务方提供并记录：

- 量表代码、名称、版本、发布日期和适用人群。
- 中文、日语、英语正式说明、题目、选项、结果解释和建议。
- 正式计分手册：反向题、权重、维度、缺失题、效度和风险规则。
- 常模来源、授权范围、适用条件、样本量、均值、标准差、版本和有效期。
- 版权/翻译/常模授权证明。
- 心理专业审核人、业务审批人和审核结论。

如果这些资料不存在，不得创建“正式支持”量表，只输出阻塞项和待补资料清单。

四、量表包和发布门禁

1. 使用现有 ScalePackage 导入/预览/确认链路，不另造平行模型。
2. 校验题号、顺序、题型、选项、分值、反向题、维度、权重、缺失策略和风险规则。
3. 校验三语内容完整性；缺少翻译的语言不能发布。
4. 校验计分公式、常模引用和结果区间；禁止重叠、循环依赖和静默降级。
5. 选择正确的 `report_template`：
   - `DEFAULT_SCREENING`
   - `SINGLE_SCORE`
   - `DIMENSION_PROFILE`
   - `NORMATIVE_PROFILE`
   - `RISK_TRIAGE`
6. 已发布或已被任务引用的量表版本不可原地修改，只能创建新版本。

五、评分和结果

1. 优先复用现有通用评分器。
2. 只有真实量表确实需要时，才补充以下能力：百分位、分段换算、条件公式、一题多维度、跳题/显示条件、数字/排序题型、效度规则。
3. 新增能力必须有版本化配置、稳定错误码、单元测试、Golden Case 和 PostgreSQL 测试。
4. 评分结果必须保存并可审计：总分、维度分、标准分/Z/T 分、常模、风险等级、结果规则、结果解释、建议和评分 trace。
5. 结果解释必须来自该量表版本的已审核内容，不能由通用风险文案替代。
6. 重新评分生成新结果和新报告，不覆盖历史结果。

六、Web 和报表

1. 报告 API 必须返回量表版本对应的模板、三语结果描述、建议、维度、常模和高风险信息。
2. Web 报告按模板显示不同区块，至少验证：
   - 单分数量表不显示无意义的维度/图表。
   - 维度量表优先显示维度画像和维度解释。
   - 常模量表显示标准分、Z 分/T 分和常模说明。
   - 风险分流量表显示高风险规则和后续处置提示。
3. Word、PDF、文本导出必须与 Web 使用同一模板语义。
4. 报告重新生成不能丢失原量表的结果解释、建议、语言和版本快照。
5. 报告中必须保留筛查不等同于临床诊断的声明。

七、Golden Case 和真实闭环验收

为该量表建立至少以下 Golden Case：

- 正常结果。
- 区间边界。
- 反向题。
- 缺失或无效答卷。
- 高风险规则。
- 结果解释、建议、维度、常模和报表模板的边界组合。

必须在真实 PostgreSQL 上验证：

1. 导入、预览、确认、双审批和发布。
2. 任务锁定具体量表版本和内容摘要。
3. 暂存、恢复、幂等提交、自动评分和报告生成。
4. 同一量表不同语言的结果和报告内容。
5. 跨租户读取/修改被拒绝，匿名任务不泄露身份。
6. 重复或并发提交只产生一个有效当前结果。
7. 重新评分保留历史结果并生成新版本。
8. Web、Word、PDF、文本四种输出与 Golden Case 预期一致。

八、最终输出

输出以下内容，禁止把未运行内容标记为完成：

- 量表代码、版本、来源、授权和专业审核状态。
- 变更文件、数据库迁移、API 兼容性和回滚方式。
- 计分能力矩阵：完全支持、部分支持、不支持、待专业审核。
- Golden Case 输入、期望分数、风险、结果解释和报表期望。
- 实际执行的 PostgreSQL、后端、Web 和 Playwright 命令及结果。
- 仍未闭环的算法、题型、常模、版权或临床治理问题。

只有在“正式资料、代码实现、数据库约束、运行验证、业务验收和专业审核”同时具备时，才能标记为正式量表闭环。
```

## 完成判定

本目标完成后，至少应有一份正式量表进入 `FULLY_SUPPORTED`；如果外部授权或专业审核尚未提供，技术实现可以完成，但状态必须保持 `BLOCKED_EXTERNAL`，不能宣称正式支持。
