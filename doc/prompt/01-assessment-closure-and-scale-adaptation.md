# 心理测评系统业务闭环与量表适配优化 Prompt

## 使用说明

将下面代码块完整交给 Codex、GitHub Copilot 或其他代码代理执行。该 Prompt 用于持续审查和优化当前工程，不得脱离实际代码编造完成状态，也不得以更换框架或全量重写代替问题修复。

```text
请根据当前心理测评系统的真实业务、真实代码、真实 PostgreSQL 结构和可运行测试，审查并修复业务闭环、量表适配、数据安全和工程可靠性问题。

当前工程主要包含：

- Kotlin、Spring Boot、显式 JDBC、PostgreSQL、Redis 后端
- React、TypeScript、Ant Design、React Query、ECharts Web 前端
- Kotlin、Jetpack Compose Android 被测者端
- 独立 auth-starter 认证与多租户模块
- Flyway 数据库迁移、GitHub Actions CI 和现有测试
- 中、日、英三语能力

目标不是为了技术先进而重写系统，也不是默认迁移到 JPA、MyBatis 或其他 ORM。必须在保持现有 API、历史 PostgreSQL 数据、多租户边界、匿名隐私、审计能力和中日英三语的前提下，完成安全、可验证、可回滚的渐进式优化。

一、强制实施原则

1. 先扫描代码、数据库、配置和测试并输出证据，再决定修改。
2. 不允许只根据类名、接口或文档判断功能已经闭环。
3. 不允许把 H2 测试当作 PostgreSQL 行为验证。
4. 不允许删除、重建或自动清空用户已有 PostgreSQL 数据库。
5. 不允许修改已经执行过的 Flyway 迁移；新增变更必须创建新版本迁移。
6. 多租户过滤、对象所有权和业务状态校验必须在代码和 SQL 中显式可见。
7. 每次修改必须可编译、可测试、可回滚，并保持 API 兼容。
8. 不允许静默降低匿名隐私、审计、幂等、可靠通知或中日英三语能力。
9. 不允许把筛查结果描述为临床诊断。
10. 量表、常模、阈值和解释规则必须有来源、版本、授权和验证记录；缺少依据时标记为待专业审核，不能伪装为正式能力。
11. 不允许通过猜测添加索引或宣称性能提升；必须保留优化前后的相同 Case 测量。
12. 发现不能仅靠代码完成的问题，例如量表版权、临床审核和应急处置责任人，必须明确列为外部治理阻塞项。

二、先建立当前真实基线

扫描整个工程并至少输出：

- 后端 Controller、Service、Repository、Worker、定时任务和异步任务数量。
- Kotlin、TypeScript、TSX、Android Kotlin 文件数和代码行数。
- 超过 500、800、1000 行的文件及其职责耦合。
- 数据库表、tenant_id、索引、唯一约束、外键、CHECK 约束和 Flyway 版本。
- 关键 SQL 的租户条件、对象所有权条件和状态条件覆盖情况。
- 单元、PostgreSQL 集成、Web 组件、Android 和 E2E 测试数量及真实运行结果。
- 量表题型、计分方法、常模策略、效度规则、导入格式和三语覆盖矩阵。
- 答卷、评分、报告、预警、干预、通知、预约和导出状态流转。
- Actuator、指标、日志、trace、告警、备份和恢复能力。

问题按 P0、P1、P2 分类。每个问题必须包含代码或配置证据、影响范围、触发条件、运行验证状态、修复方案、风险和回滚方式。

三、业务闭环审查

逐条验证以下主链路，不允许因为单个接口存在就判定闭环：

任务创建 -> 量表版本锁定 -> 目标分配 -> 被测者可见 -> 暂存答卷 -> 幂等提交 -> 自动评分 -> 报告生成 -> 风险判定 -> 预警创建 -> 负责人分配 -> 干预记录 -> 状态关闭 -> 全程审计。

每个节点必须检查：

- 前置状态、合法状态转换和禁止操作。
- 租户、角色、对象所有权和匿名访问边界。
- 重复请求、并发请求、超时、进程崩溃和重试行为。
- 事务范围，以及事务中是否等待邮件、Push、对象存储或其他网络调用。
- 失败后是否可恢复、可重放、可查询和可审计。
- Web、Android 与后端 DTO、错误码、可空字段和三语文案是否一致。

至少实现并验证：

1. 只有通过发布校验的不可变量表版本才能创建任务。
2. 任务创建后固定量表版本，后续编辑量表不得改变历史答卷解释。
3. 保存、提交、超时提交和重新测评规则统一由明确策略控制。
4. 提交使用稳定幂等键和数据库唯一约束；并发提交只能生成一个结果。
5. 匿名答卷不得持久化可直接反查身份的数据，不生成可识别个人报告或个人通知。
6. 重新评分生成新的计算版本和审计记录，不覆盖历史结果。
7. 风险和预警的创建必须幂等；预警分配、升级、干预和关闭使用明确状态机。
8. 异步任务采用 Transactional Outbox 或等价机制，支持原子领取、超时回收、指数退避、死信和人工重放。
9. 外部调用配置连接、读取和整体超时，错误信息必须脱敏。

四、多租户与数据归属

多租户是 P0，不允许只给表增加 tenant_id 就宣称完成。

1. 输出每张业务表的租户归属来源、推导率、孤儿行、冲突行和无法映射行。
2. 对历史数据先做只读预检查，再回填；无法确定归属的数据进入隔离清单，不得猜测。
3. 新增写入必须同步写 tenant_id，不能只依赖历史回填。
4. 列表、详情、更新、删除、批量操作、导出和 Worker 查询必须显式限制租户。
5. 访问子对象时必须通过父对象链验证所属租户，不能只验证请求中的 tenantId。
6. 超级管理员例外必须集中定义并审计，不能散落在 Repository 中。
7. 为每个重要 Controller Case 增加：同租户成功、跨租户拒绝、对象不存在、超级管理员例外、匿名隐私测试。
8. tenant_id 的 NOT NULL、外键验证和唯一约束应分阶段执行，避免长时间锁表。

五、通用量表包模型

建立可版本化、可校验、可测试的 ScalePackage，至少包含：

- 量表代码、名称、版本、来源、版权、授权范围、适用人群和发布日期。
- 中、日、英三语的量表说明、题目、选项、结果解释和建议。
- 题型、必答、跳题、显示条件和答案合法性规则。
- 原始分、反向题、权重、维度归属和维度聚合规则。
- 缺失题处理、最大缺失率、无效答卷和异常作答时长规则。
- 总分、维度分、标准分、Z 分、T 分、百分位和自定义公式定义。
- 常模代码、适用年龄、性别、地区、语言、组织、样本量、均值、标准差和版本。
- 效度量表、一致性、矛盾回答和其他质量规则。
- 结果区间、风险等级、解释、建议和预警触发规则。
- Golden 测试样例、期望中间分、期望最终分、期望风险和来源。
- 发布审批人、专业审核人、发布时间和审计记录。

任务必须引用具体 scale_version_id。已经发布或被任务引用的版本不可原地修改，只能复制产生新版本。

六、计分引擎能力

通用引擎至少支持：

1. 简单求和、平均、加权、反向计分和系数组合。
2. 多维度计分，同一道题可按明确规则参与一个或多个维度。
3. 条件公式、分段换算、标准分、Z 分、T 分和百分位。
4. 常模按年龄、性别、地区、语言或组织条件选择，并有明确优先级和兜底策略。
5. 必答、允许缺失、按比例折算、无效答卷和无法评分结果。
6. 单选、多选、矩阵、数字、排序、文本和跳题；文本题默认不参与评分，除非有明确规则。
7. 计分过程输出可审计的中间结果：题目原始分、反向分、加权分、维度分、常模选择和最终解释规则。
8. 不支持的计分方法必须阻止发布或明确报错，禁止静默退化为简单求和。
9. 量表专用算法通过有版本的受限扩展点实现，不允许任意脚本直接访问数据库、文件或网络。

PHQ、GAD 等简单累加量表可使用通用规则。SCL、EPQ、16PF、MMPI 等必须根据正式手册实现专用维度、常模、效度和解释规则；没有授权数据和专业验证时，不得宣称正式支持。

七、量表导入和发布门禁

支持人工维护和受控导入，但导入成功不等于可发布。

发布前必须验证：

- 量表代码、版本、适用范围、来源和授权信息完整。
- 三语必填内容完整；允许缺少翻译时必须显式标记不可使用的语言。
- 题号唯一、顺序合法、题型和答案格式匹配。
- 选项分值、反向题范围、权重、维度引用和跳题目标合法。
- 计分公式可解析，所有变量有来源，不存在循环依赖。
- 常模条件不冲突，所需常模完整，样本和版本信息可追溯。
- 结果区间无重叠；是否允许间隙必须显式配置。
- 风险规则与结果规则不互相矛盾。
- 至少一组正常、边界、反向、缺失、无效和高风险 Golden Case 全部通过。
- 专业人员和业务管理员完成双重审批。

发布后保存不可变内容摘要。运行时和审计记录均保存该摘要，用于证明评分使用了哪一版内容。

八、临床安全和隐私

1. 所有报告明确说明筛查不等同于诊断。
2. 自伤、自杀等高风险规则必须配置人工复核、通知对象、响应时限、升级路径和处置记录。
3. 匿名任务必须说明匿名边界；若业务要求后续识别个体，就不能称为完全匿名。
4. 身份信息与答卷数据应最小化关联，报告、日志、导出和错误信息不得泄露敏感答案。
5. 报告查看、导出、重新评分、预警查看和人工重放必须记录安全审计。
6. 数据保留、删除、撤回同意、导出和备份恢复需要明确策略。
7. 版权、授权、常模来源和专业审核属于上线门禁，不能用技术实现替代。

九、测试与验收

必须在真实 PostgreSQL 上验证：

- Flyway 空库安装和已有基线升级。
- 历史数据预检查、回填和冲突阻断。
- 并发保存、并发提交、重复 submitToken 和 Worker 崩溃恢复。
- 同租户、跨租户、超级管理员和匿名访问矩阵。
- 量表发布门禁和全部 Golden Case。
- 任务到干预关闭的端到端业务 Case。
- 中、日、英三种语言下 Web、Android、接口错误和报告内容。

核心 E2E 至少覆盖：

1. 管理员发布量表、创建任务并分配用户。
2. 被测者暂存、恢复、提交并查看允许查看的报告。
3. 重复和并发提交只产生一个有效结果。
4. 高风险结果创建一个预警，分配负责人，记录干预并关闭。
5. 匿名提交不能通过业务接口、通知、报告、导出或日志反查身份。
6. 跨租户用户无法读取或修改量表、任务、答卷、报告、预警和导出。
7. 通知、导出或对象存储暂时失败后可以自动恢复或进入死信并人工重放。

十、性能、可观测性和恢复

1. 使用隔离 PostgreSQL 和真实规模合成数据测量任务列表、答卷提交、评分、预警、统计、趋势、导出、通知和预约。
2. 记录 p50、p95、p99、吞吐、连接池、JVM 内存和数据库资源。
3. 使用 pg_stat_statements 和 EXPLAIN (ANALYZE, BUFFERS) 决定索引。
4. 深分页评估 keyset pagination；批量操作限制批次和内存。
5. 大导出使用流式生成和存储，避免完整 ByteArray 常驻 JVM。
6. 指标至少包含提交成功率、评分失败、预警处理时延、队列长度、重试、死信、导出耗时和数据库连接池。
7. 建立 correlation id、结构化日志、低基数指标、SLO 和告警规则。
8. 实测数据库备份恢复、对象文件恢复和应用回滚，并记录 RPO、RTO 和恢复步骤。

十一、渐进实施顺序

阶段 1：修复会造成串租户、重复结果、匿名泄露、错误评分或无法恢复的 P0。

阶段 2：完成量表包、发布门禁、版本冻结、Golden Case 和专业审批链。

阶段 3：补真实 PostgreSQL 集成测试和核心业务 E2E。

阶段 4：按职责拆分超大 Repository、Service、页面和 Android UI 状态，但保持 API 契约。

阶段 5：建立真实性能基线、可观测性、部署回滚和备份恢复演练。

每个阶段都必须：

- 先列出计划修改文件、数据库影响和兼容性风险。
- 使用小批次修改，保持每一步可编译和可测试。
- 给出实际执行命令和结果，不得只写“理论上通过”。
- 更新文档中的真实完成状态和剩余问题。
- 不得把尚未运行验证的内容标记为完成。

十二、最终交付格式

最终输出必须包含：

1. 当前基线和 P0/P1/P2 问题清单。
2. 已修复问题、对应代码和数据库迁移。
3. API 兼容性、数据影响和回滚方式。
4. 实际执行的构建、测试、PostgreSQL 和 E2E 结果。
5. 量表能力矩阵：完全支持、部分支持、不支持、待专业审核。
6. 仍未闭环的问题及原因。
7. 需要业务负责人、心理专业人员、运维或法务完成的外部事项。

只有同时满足“代码实现、数据库约束、运行验证、业务验收和专业审核”的功能，才能标记为完全闭环。
```
