- 中、日、英三语能力
- 量表、任务、答卷、评分、报告、风险预警、干预、通知、预约和导出功能

- 心理评测业务正确性

## 二、强制实施原则

必须遵守：

1. 先扫描、运行和输出证据，再修改。
2. 不允许把筛查结果表述为临床诊断。
3. 不允许把某一种量表的指标、阈值和解释应用到其他量表。
4. 不允许由前端重新计算心理测评分数或自行推导风险等级。
5. 量表、常模、阈值、解释规则必须有来源、版本、授权和专业审核状态。
6. 缺少依据时必须标记“待专业审核”，不能使用猜测性默认值。
7. 不得修改已经执行过的 Flyway 迁移；数据库变更必须新增迁移。
8. 不得删除、重建或自动清空已有 PostgreSQL 数据。
9. 多租户、对象所有权和业务状态检查必须在代码和 SQL 中显式可见。
10. 不允许降低匿名隐私、审计、幂等、三语和可靠通知能力。
11. 所有修改必须保持现有 API 兼容；必要时使用新增字段或版本化接口。
12. 每批修改必须可编译、可测试、可回滚。
13. 不允许把 H2 测试结果当作 PostgreSQL 行为验证。
14. 未实际运行的测试不得标记为通过。
15. 版权、量表授权、临床审核和应急责任人等不能靠代码解决的事项，必须列为外部阻塞项。
16. 不得无理由全量重写大页面；拆分必须基于真实职责和业务边界。

## 四、优先核查当前已发现的高风险问题

以下是需要重点验证的问题候选。不得直接假定描述一定正确，必须以当前工作树代码和运行结果确认。

### 4.1 通用报告疑似错误套用 SCL-90 指标

重点检查：

- `admin-web/src/pages/ReportDetailPage.tsx`
- 报告 DTO
- 评分服务
- 导出服务
- 报告生成服务

当前代码可能在前端统一计算：

- GSI
- PST
- PSDI
- `GSI < 1.5`
- `PST < 43`
- 所有维度固定临界值 `2.0`

必须确认这些指标是否被错误应用到所有量表。

修复要求：

1. 前端不得根据答案重新计算心理测评分数。
2. 后端评分引擎负责输出完整、可审计的计算结果。
3. 报告只展示当前量表版本明确定义的指标。
4. API 建议以兼容方式新增 `scaleVersionId`、`scaleCode`、`calculationVersion`、`normVersion`、`contentHash` 和 `metrics` 等字段。
5. 每个指标至少包含稳定代码、三语名称、原始值、显示值、参考依据和解释代码。
6. GSI、PST、PSDI 只能由明确声明支持这些指标的量表显示。
7. 缺少专业验证时，报告显示“待专业审核”，不能使用默认阈值。
8. 导出文件不得硬编码 `SCL-90` 文件名或标题。

### 4.2 风险等级枚举不一致

扫描所有：

- `NORMAL`
- `LOW`
- `ATTENTION`
- `MODERATE`
- `MEDIUM`
- `HIGH`
- `CRITICAL`
- `P0/P1/P2`

检查以下问题：

- 前端是否只识别部分等级
- 未识别等级是否错误显示为绿色或低风险
- 评分、报告、统计、预警、通知和导出排序是否一致
- `ATTENTION` 是否在风险排序中落入默认等级
- 颜色是否成为唯一风险表达方式

建立统一风险模型，至少包含：

- 稳定风险代码
- `severityRank`
- 中日英名称
- 展示颜色和图标
- 是否创建预警
- 响应时限
- 处置策略代码
- 是否需要立即人工复核

数据库、后端、Web、Android、导出和统计必须使用同一套定义。

### 4.3 心理答卷疑似明文保存在 localStorage

重点检查：

- `admin-web/src/pages/TaskQuestionPage.tsx`
- 所有 `localStorage`、`sessionStorage` 和 IndexedDB 使用
- Android 本地存储
- 日志、错误上报和埋点

修复要求：

1. 服务端草稿作为权威数据源。
2. Web 使用防抖自动保存。
3. 浏览器本地只允许保存非敏感游标，例如 `taskId`、`answerSheetId` 和 `currentIndex`。
4. 不得把选项答案、文本答案、风险答案明文长期保存到 localStorage。
5. 提交成功、退出登录、匿名会话结束时清除本地状态。
6. 如果业务必须支持离线答题，必须单独设计用户明确同意、短 TTL、本地加密、密钥和 XSS 威胁模型、自动清除及同步冲突策略。
7. 日志、错误上报、审计和异常信息不得包含敏感答案。

### 4.4 Android 提交幂等疑似不稳定

重点检查 Android 最终提交时是否每次点击都生成新的 UUID。

修复要求：

1. 每张答卷只生成一个稳定 submit token。
2. token 在提交结果明确成功或明确失败前持续保存。
3. 网络超时后先按 token 查询最终提交状态。
4. 不得因为用户重试而创建新的有效结果。
5. Web 和 Android 必须使用一致的幂等语义。
6. 增加 PostgreSQL 并发提交测试。

## 五、心理安全和高风险处置闭环

评分产生高风险结果后，不能只显示红色提示或发送普通通知。

建立版本化 `SafetyResponsePolicy`，至少包含：

- 触发规则和规则版本
- 风险等级
- 适用量表和量表版本
- 是否要求立即人工复核
- 负责人角色
- 默认责任团队
- 首次响应 SLA
- 升级时限
- 联系失败升级策略
- 地区、语言对应的求助资源
- 是否需要安全计划
- 是否需要紧急评估
- 随访时间
- 关闭条件

高风险链路必须验证：

风险触发 → 幂等创建预警 → 分配负责人 → SLA 开始计时 → 人工安全评估 → 记录联系尝试 → 选择处置结果 → 转介或升级 → 48/72 小时随访 → 满足关闭条件 → 完整审计。

工作人员页面需要显示：

- 风险等级和依据
- 待响应倒计时
- 当前负责人
- 联系次数和结果
- 通知失败状态
- 是否超过 SLA
- 升级对象
- 安全评估结论
- 随访时间
- 关闭检查清单

被测者页面需要：

- 平静、非污名化的说明
- “筛查结果不等于诊断”
- 明确下一步行动
- 适用于当前地区和语言的求助资源
- 高风险时醒目的立即求助入口
- 只有在运营上真正能够保证时，才能显示“工作人员将在某时间联系你”

禁止仅凭自动评分直接向用户显示“确诊”“患有某疾病”等内容。

参考：

- NIMH ASQ Toolkit：<https://www.nimh.nih.gov/research/research-conducted-at-nimh/asq-toolkit-materials>
- NIMH Adult Outpatient Brief Suicide Safety Assessment：<https://www.nimh.nih.gov/research/research-conducted-at-nimh/asq-toolkit-materials/adult-outpatient/adult-outpatient-brief-suicide-safety-assessment-guide>
- WHO Digital Health Guideline：<https://www.who.int/news/item/17-04-2019-who-releases-first-guideline-on-digital-health-interventions>

## 六、Web 答题页面优化

保留当前“一题一页”、移动端大按钮和服务端草稿能力，但重新审查完整交互。

### 6.1 开始测评前

增加开始说明页：

- 量表名称和用途
- 预计耗时
- 截止时间
- 是否允许暂存
- 是否允许返回修改

- 高风险情况下系统会采取什么行动
- 求助资源
- 同意开始按钮

### 6.2 答题过程

默认要求：

- 上一题
- 下一题
- 明确保存状态
- 最后保存时间
- 当前题号和总题数
- 剩余时间或截止时间
- 错误定位
- 支持键盘操作
- 选中状态不能只用颜色表达

取消默认自动跳题。

如果特定量表确实要求自动跳题或禁止返回，必须：

- 由量表版本配置
- 有专业审核记录
- 开始前明确告知用户
- 不得由页面写死

### 6.3 最终确认页

最终确认页必须展示：

- 每道题的回答状态
- 所选答案摘要
- 未回答题目标记
- 修改入口
- 匿名和隐私提醒
- 明确的最终提交确认

不能只显示“已回答多少题”。

检查多选题是否导致回答题数错误。回答数量必须按唯一且完整的题目数量计算，而不是按答案条目数量计算。

### 6.4 超时和异常

- 服务端时间作为截止时间权威来源。
- 到期前进行可配置提醒。
- 到期前自动保存。
- 超时提交进入“正在确认结果”状态。
- 按 submit token 轮询最终结果。
- 不允许用户因为超时重复产生多个结果。
- 是否允许延期必须由任务策略明确配置。
- 不允许用模糊提示掩盖实际失败状态。

### 6.5 无障碍

按照 WCAG 2.2 检查：

- 题目切换后的焦点管理
- 错误信息与字段关联
- 保存和提交状态的 `aria-live`
- 键盘操作
- 200% 缩放
- 移动端固定栏是否遮挡焦点元素
- 颜色对比度
- 点击目标尺寸
- `lang` 属性
- 动画与 `prefers-reduced-motion`

参考：

- <https://www.w3.org/WAI/WCAG22/Understanding/status-messages>

## 十、量表发布门禁

将当前大型量表维护页面按业务职责改造成六步“量表工作台”：

1. 基本信息、来源、授权和适用人群
2. 中日英量表内容
3. 题目、维度、计分和效度规则
4. 常模、结果区间和风险处置
5. Golden Case 和评分模拟器
6. 专业审批、业务审批和发布

发布前必须验证：

- 来源和授权完整
- 三语内容完整
- 题号和顺序合法
- 题型和选项格式合法
- 分值范围合法
- 反向题配置合法
- 维度引用合法
- 跳题目标存在
- 公式可解析
- 不存在循环依赖
- 常模条件不冲突
- 结果区间不重叠
- 风险规则不矛盾
- 所有 Golden Case 通过
- 专业审核完成
- 业务审核完成

发布后：

- 内容不可原地修改
- 保存不可变内容摘要
- 任务引用具体 scaleVersionId
- 修改只能复制产生新版本
- 历史答卷始终使用原始版本解释

每个量表显示能力状态：

- 完全支持
- 部分支持
- 不支持
- 待专业审核
- 缺少授权
- 缺少常模
- 缺少翻译
- Golden Case 未通过

## 十一、Golden Case

每个量表版本必须至少提供：

- 正常样例
- 最低边界
- 最高边界
- 阈值上下边界
- 反向题
- 缺失题
- 无效答卷
- 高风险题
- 多维度样例
- 常模匹配样例
- 常模兜底样例

每个 Case 保存：

- 输入答案
- 每题期望分
- 维度期望分
- 常模选择
- 最终分数
- 风险等级
- 解释规则
- 来源
- 专业审核人

模型生成或开发人员推导的 Case 只能标记为 `needs_review`，不能自动成为正式 Golden Case。

## 十二、报告画面重新设计

报告分成三个视图。

### 12.1 被测者视图

优先显示：

- 非诊断声明
- 当前状态的通俗解释
- 下一步建议
- 是否建议专业咨询
- 预计跟进方式
- 高风险立即求助入口
- 数据和隐私说明

技术指标默认折叠，不应成为第一屏主体。

### 12.2 专业人员视图

显示：

- 原始分
- 维度分
- 标准分
- 常模
- 效度和质量信息
- 风险依据
- 历史趋势
- 人工备注
- 是否完成复核

### 12.3 审计视图

显示：

- scaleVersionId
- calculationVersion
- normVersion
- contentHash
- 语言
- 发布时间
- 专业审核人
- 重新评分记录
- 导出记录
- 查看记录

匿名任务不得显示姓名、用户编号或可反查身份的信息。

## 十三、中日英翻译质量

不能只验证“有字符串”，还必须验证语义正确。

重点扫描：

- 心理学术语
- 风险等级
- 普查、筛查、评测
- 匿名能力
- 已回答题数
- 报告解释
- 求助和危机文案

特别注意日语中不能把心理“筛查/普查”误译为电影“上映”。

建立：

- 翻译 key 完整性测试
- 禁止回退测试
- 占位符一致性测试
- 日文长度和布局测试
- 专业术语表
- 心理专业人员或母语审核状态

## 十四、测试要求

必须在真实 PostgreSQL 上验证：

1. Flyway 空库安装
2. 已有基线数据库增量升级
3. 并发保存
4. 并发提交
5. 重复 submit token
6. 网络超时后的结果查询
7. Worker 崩溃恢复
8. 同租户成功
9. 跨租户拒绝
10. 匿名访问边界
11. 匿名报告和导出不可反查身份
12. 每个量表 Golden Case
13. 风险等级全枚举
14. 高风险只创建一个预警
15. 预警 SLA、升级、干预和关闭
16. Web 三语答题和报告
17. Android 三语答题和报告
18. 键盘和 TalkBack
19. 200% 字体和小屏幕
20. 截止时间和超时提交

核心 E2E：

管理员导入量表 → 完成发布校验 → 专业审核 → 业务审核 → 发布不可变版本 → 创建任务并锁定版本 → 被测者开始测评 → 暂存和恢复 → 最终确认 → 幂等提交 → 后端评分 → 报告生成 → 风险判断 → 高风险预警 → 负责人处理 → 安全评估 → 随访 → 关闭 → 审计和导出。

## 十五、渐进实施顺序

### 阶段 1：P0 临床和数据安全

- 修正报告错误指标
- 统一风险枚举
- 移除浏览器敏感答案
- 修复 Android submit token
- 补高风险处置策略和 SLA

### 阶段 2：答题体验

- 上一题
- 最终确认
- 取消不安全的默认自动跳题
- 自动保存状态
- 超时确认
- 无障碍

### 阶段 3：ScalePackage

- 多语言量表内容
- 版权和授权
- 缺失与效度规则
- 常模版本
- 专用算法扩展点
- 不可变版本和内容摘要

### 阶段 4：发布门禁

- Golden Case
- 评分模拟器
- 专业审批
- 业务审批
- 发布就绪度

### 阶段 5：管理和报告画面

- 量表工作台
- 用户报告
- 专业报告
- 风险处置工作台
- 审计视图

每个阶段开始前必须列出：

- 计划修改文件
- 数据库迁移
- API 变化
- 数据影响
- 兼容性风险
- 回滚方式

每个阶段结束后必须实际执行构建、测试和 PostgreSQL 验证。

## 十六、最终交付格式

最终输出必须包含：

1. 当前真实基线
2. P0/P1/P2 问题清单
3. 已修复问题和文件
4. 新增 Flyway 迁移
5. API 兼容性说明
6. 数据影响
7. 回滚方法
8. 实际执行命令
9. 实际构建和测试结果
10. PostgreSQL 验证结果
11. Web 和 Android 画面验证结果
12. 量表能力矩阵
13. 完全支持、部分支持和不支持的量表能力
14. 尚未闭环的问题
15. 需要心理专业人员完成的事项
16. 需要业务负责人完成的事项
17. 需要法务确认的版权和授权事项
18. 需要运维落实的高风险值班、告警和恢复事项

只有同时满足以下条件，功能才能标记为“完全闭环”：

- 代码实现
- 数据库约束
- API 契约
- PostgreSQL 运行验证
- Web 和 Android 验证
- 自动化测试
- 业务验收
- 心理专业审核
- 版权和授权确认
- 高风险运营责任落实

尚未运行、尚未审核或尚未获得授权的能力，必须明确标记为未完成，不得以“代码已经存在”代替闭环结论。
