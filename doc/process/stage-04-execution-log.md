异步处理建议：

适合异步处理的环节：

1. 通知投递
- 任务提醒
- 预警提醒
- 预约提醒

2. 导出生成
- Excel 导出
- PDF 导出

3. 群体统计聚合
- 大批量统计计算
- 趋势汇总

当前建议同步处理的环节：

1. 答卷提交后的自动评分
2. 系统报告生成
3. 预警主记录生成

原因：

- 这些属于主链路核心体验
- 当前目标要求整体在短时间内完成
- 第一阶段系统规模下可以先保持同步实现

导出与通知实现建议：

1. 导出
- 第二阶段引入
- 优先支持 Excel
- PDF 报告导出可作为补充能力
- 导出必须记录审计日志

2. 通知
- 当前建议先实现站内消息
- 小程序订阅消息、短信、邮件可作为后续扩展
- 通知统一由 `notification` 模块管理

预警与预约闭环扩展方案：

1. 预警生成后进入待处理状态
2. 管理员或系统分配责任人
3. 咨询师接单
4. 必要时发起预约或录入干预记录
5. 咨询完成后填写咨询记录
6. 必要时安排复测
7. 最终结案或继续跟进

第二阶段实现顺序建议：

1. 预警分配与状态流转
2. 咨询预约与咨询记录
3. 通知模块
4. 统计与群体报告
5. 导出与审计

数据安全与权限边界：

1. 预约、咨询、干预记录默认属于敏感数据
2. 咨询师只查看授权对象
3. 管理者优先查看群体统计，不默认看个体敏感详情
4. 导出与敏感查看必须保留审计日志

发现问题：
- 如果第二阶段一开始就同时做预约、通知、统计、导出，范围仍然偏大，建议按闭环顺序拆开
- 群体统计容易膨胀成复杂 BI，当前阶段应控制在业务看板和基础分析层
- 通知通道过多会拉高复杂度，建议先做站内消息，再考虑外部通道
