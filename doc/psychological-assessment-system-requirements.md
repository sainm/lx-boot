# 高校/企业心理测评与预警系统需求整理

## 1. 文档目的

本文档用于整理当前对话中已经明确的项目方向、需求范围、角色划分、核心模块与后续落地方向，作为后续产品设计、数据库设计、原型设计与开发实现的基础。

本文档同时作为需求来源总文档保留；部分细化内容已在 `doc/01-09` 结构化设计文档中展开，后续详细设计优先以结构化文档为准。

同时，本文档补充记录一个重要实现约束：

- 用户管理能力基于 `auth-starter` 基础工程扩展实现
- 本项目不从零重新设计认证、授权与基础账号体系，而是在既有能力之上对业务字段、业务角色与业务流程进行集成

## 2. 对话背景整理

本轮对话中，首先围绕“心理评测系统”进行了头脑风暴，并对项目方向进行了收敛。初始阶段提出了三个候选方向：

- 面向个人用户的自助测评平台
- 面向学校/企业的团体心理筛查系统
- 面向心理咨询师或机构的专业辅助工具

在进一步收敛后，最终确定的项目方向为：

**高校/企业心理测评与预警系统**

该方向兼顾了业务场景完整性、角色层次清晰度、功能模块丰富度以及项目落地可行性，适合作为课程设计、毕业设计或中小型业务系统原型。

## 3. 项目定位

高校/企业心理测评与预警系统，面向学校心理中心、辅导员体系、企业 HR 或 EAP 场景，提供批量组织心理测评、自动评分分析、风险对象识别与后续干预跟踪能力。

系统目标不是简单的在线答题，而是形成“测评发起 -> 数据采集 -> 自动分析 -> 风险预警 -> 干预跟踪”的闭环。

在技术实现层面，账号、登录、权限、组织等基础能力优先复用 `auth-starter`，业务系统重点建设心理测评、报告分析、预警干预等上层业务模块。

## 4. 项目目标

结合当前对话，系统的核心目标可归纳为以下四点：

### 4.1 提高测评组织效率

- 支持管理员按班级、学院、部门、岗位等组织单位批量发起测评
- 降低纸质量表、线下统计与人工汇总的成本

### 4.2 提供自动评分与报告生成能力

- 用户完成答题后自动计算分数
- 按量表规则计算总分、维度分、风险等级
- 生成个人报告与群体分析结果

### 4.3 实现风险预警

- 对高风险测评结果进行自动识别与标记
- 形成预警名单，供心理老师、咨询师或相关负责人查看
- 避免高风险个体被遗漏

### 4.4 支撑后续跟踪管理

- 支持复测记录
- 支持访谈、干预、转介等处理记录
- 支持状态闭环管理，而不是一次测评后结束

## 5. 适用场景

### 5.1 高校场景

- 新生心理普查
- 学期心理健康筛查
- 特定学院、班级或宿舍群体专项筛查
- 重点关注学生复测与干预记录

### 5.2 企业场景

- 员工心理健康普查
- 高压岗位或重点部门心理风险筛查
- 培训期、晋升期、重大项目期的压力测评
- 企业 EAP 配套管理

## 6. 角色划分

根据当前讨论，系统可包含以下角色：

### 6.1 普通用户

对应学生或员工，主要功能包括：

- 接收测评任务
- 在线答题
- 查看个人测评结果或报告
- 接收复测提醒

### 6.2 测评管理员

主要功能包括：

- 创建和发布测评任务
- 管理量表
- 组织用户参与测评
- 查看群体统计结果

### 6.3 心理老师 / 咨询师 / EAP 专员

主要功能包括：

- 查看预警名单
- 访问个体测评记录
- 记录访谈、干预和转介信息
- 跟踪处理状态

其中“咨询师”角色可作为重点业务角色单独强调，除查看结果外，还应承担以下职责：

- 查看被分配或有权限访问的个体测评报告
- 结合量表结果进行人工研判
- 记录咨询过程、建议和阶段性结论
- 跟踪复测结果与风险变化
- 对需要进一步处理的对象执行转介或结案操作

### 6.4 系统管理员

主要功能包括：

- 用户与角色管理
- 组织结构管理
- 权限控制
- 系统日志与审计管理

### 6.5 基础角色与业务角色的关系

由于用户管理基于 `auth-starter` 扩展，因此角色体系建议拆分为两层：

- 基础安全角色：由认证授权底座负责，例如 `SUPER_ADMIN`、`ADMIN`、`USER`
- 业务应用角色：由心理测评系统负责映射与使用，例如学生、员工、心理老师、辅导员、HR、测评管理员

建议在实现中避免将所有业务含义直接硬编码到底层认证模块，而是通过角色、权限或业务扩展表进行映射，降低耦合度。

## 7. 核心业务流程

结合已有讨论，系统主流程可定义为：

1. 管理员创建测评任务
2. 选择量表、参与对象、时间范围和规则
3. 学生或员工在线完成答题
4. 系统根据量表规则自动评分
5. 生成个人结果、群体统计与风险等级
6. 对高风险对象进入预警列表
7. 心理老师或相关人员进行人工复核与干预记录
8. 必要时安排复测、转介或结案

## 8. 功能模块整理

根据对话内容，系统建议至少包含以下功能模块。

### 8.1 用户与组织管理

- 基于 `auth-starter` 的用户注册、登录、密码管理与权限控制能力
- 学生 / 员工基础档案管理
- 班级、学院、部门、岗位等组织结构维护
- 用户分组与批量导入
- 用户与组织、角色、业务身份的关联管理

### 8.1.1 复用 `auth-starter` 的能力范围

根据当前对 `auth-starter` 基础工程的梳理，可直接复用或优先集成的能力包括：

- 用户注册、密码登录、JWT 鉴权、刷新令牌、退出登录
- 修改密码、管理员重置密码
- 登录失败锁定策略
- 用户、角色、权限管理接口
- 组织与租户能力，包括 `tenant` 和 `group`
- 登录日志与安全事件审计

这些能力说明本项目在“用户管理”部分应以集成为主，而不是重复开发认证中台。

### 8.1.2 业务侧需要补充的用户信息

`auth-starter` 已具备通用账号与组织能力，但心理测评系统仍需补充自身业务信息，建议通过业务表扩展，而不是直接破坏底层通用模型。可补充的字段或实体包括：

- 用户业务类型，例如学生、教职工、员工、咨询师
- 学号 / 工号
- 学院、班级、部门、岗位等业务归属
- 是否重点关注对象
- 最近一次测评时间
- 最近一次风险等级
- 干预跟踪状态

建议采用“认证底座用户表 + 业务扩展资料表”的方式实现。

### 8.2 量表管理

- 量表基本信息管理
- 题目管理
- 选项与分值配置
- 评分规则配置
- 量表版本管理
- 维度配置与维度分计算
- 量表导入

### 8.2.1 量表模块的业务特点

根据当前补充需求，量表模块不是简单的“题目集合”，而是需要支持较灵活的结构化建模。至少需要考虑以下两类复杂性：

- 不同量表可能存在不同的分数计算方式
- 同一个量表内部可能包含多个维度，且维度需要独立计分、解释与展示

因此，量表管理应支持“量表 -> 维度 -> 题目 -> 选项 -> 计分规则”的分层设计，而不是只保存一张量表主表和一张题目表。

### 8.2.2 量表的基本组成

一个完整量表建议包含以下元素：

- 量表基础信息：名称、编码、简介、适用对象、说明、状态、版本
- 维度信息：维度名称、维度编码、维度说明、排序
- 题目信息：题干、题型、所属维度、题号、是否必答
- 选项信息：选项内容、显示顺序、原始分值
- 评分规则：总分规则、维度分规则、反向计分规则、风险分级规则
- 结果解释：总分解释、维度解释、风险提示、建议模板

### 8.2.3 维度支持要求

量表需要支持“维度”这一核心概念。维度可理解为量表内部的子能力、子特征或子风险指标，例如：

- 情绪状态
- 压力水平
- 人际关系
- 睡眠情况

围绕维度，系统建议支持以下能力：

- 一个量表可配置多个维度
- 每道题可归属某一个维度，必要时可扩展支持无维度归属
- 每个维度可以独立计算得分
- 每个维度可以配置单独的结果解释
- 报告中既展示总分，也展示各维度得分及分析

### 8.2.4 计分规则差异支持

不同量表可能采用不同的计分策略，系统设计时需要预留扩展性。当前至少应考虑以下情况：

- 直接累加计分：选项分值直接累加形成总分
- 维度汇总计分：先计算维度分，再汇总或映射为总结果
- 反向计分：部分题目采用反向分值
- 区间分级：根据分数区间映射正常、关注、高风险等等级
- 结果分档：根据规则输出轻度、中度、重度等结论标签

后续如果需要支持更复杂量表，还可以进一步扩展：

- 不同题目权重
- 不同维度权重
- 按常模换算
- 原始分与标准分双轨输出

因此，量表评分规则不建议写死在代码中，而应尽量做成可配置或可扩展的规则模型。

### 8.2.5 报告展示要求

由于量表包含维度和差异化计分规则，报告展示至少应包括：

- 量表总分
- 各维度得分
- 风险等级
- 总体解释
- 各维度解释
- 建议或干预提示

对于团体统计，还应支持：

- 量表总分分布统计
- 各维度均值与分布统计
- 不同组织下的维度对比分析

### 8.2.6 量表导入功能

系统需要提供“导入量表”能力，用于将已有心理量表快速录入系统，减少管理员手工逐题维护的成本。

量表导入适用场景包括：

- 初始系统建设时批量导入常用量表
- 从已有 Excel 或模板资料迁移量表
- 新增专业量表时快速录入题目、维度与规则

### 8.2.7 导入内容范围

量表导入不应只导入量表名称和题目，还应尽可能覆盖完整结构，建议支持导入以下内容：

- 量表基础信息
- 维度信息
- 题目信息
- 题目所属维度
- 选项与分值
- 反向计分标记
- 分数区间与风险等级规则
- 报告解释模板

### 8.2.8 导入方式建议

后续实现时，建议至少支持模板化导入，例如：

- Excel 导入
- CSV 导入
- JSON 结构化导入

其中最适合业务人员使用的通常是 Excel 模板导入。

### 8.2.9 导入校验要求

导入量表时应进行必要的数据校验，避免错误规则进入系统。建议至少校验：

- 量表编码是否重复
- 维度编码或名称是否重复
- 题号是否重复
- 题目是否存在未绑定维度的异常情况
- 选项分值是否完整
- 反向计分配置是否正确
- 风险分级区间是否连续或冲突
- 必填字段是否缺失

### 8.2.10 导入后的处理建议

量表导入完成后，建议系统提供：

- 导入结果反馈
- 错误明细提示
- 草稿状态或待发布状态
- 导入后预览
- 发布前人工复核

这样可以降低错误量表直接进入正式测评流程的风险。

### 8.3 测评任务管理

- 创建测评任务
- 选择适用量表
- 指定测评对象
- 设置开始时间、截止时间、是否匿名
- 查看任务完成进度

### 8.3.1 测评分配方式

根据当前补充需求，管理员应支持两种主要的测评分配方式：

- 按组分配测评
- 按个人分配测评

其中“组”可结合 `auth-starter` 的组织能力实现，映射为班级、学院、部门、岗位组或其他业务分组。

### 8.3.2 按组分配

按组分配适用于高校班级、学院、宿舍群体，或企业部门、岗位群体等批量测评场景。建议支持：

- 选择一个或多个组作为测评对象
- 自动将组内用户纳入任务范围
- 查看组级完成率
- 统计未参与人员名单
- 允许后续对组内个别人进行补发

### 8.3.3 按个人分配

按个人分配适用于重点关注对象、复测对象、咨询跟踪对象等精细化场景。建议支持：

- 直接选择一个或多个个人用户发起测评
- 支持针对特定对象补发量表
- 支持对高风险或待复测对象定向下发任务
- 支持咨询师后续跟踪个体测评历史

### 8.3.4 分配对象模型建议

为了同时支持按组和按个人分配，测评任务设计时建议拆分为：

- 测评任务主表：描述任务基本信息
- 测评任务分配表：描述任务具体分配对象

任务分配表中建议兼容两类目标：

- `group` 目标：表示按组分配
- `user` 目标：表示按个人分配

这样可以避免为不同分配方式拆成两套完全独立的任务模型。

### 8.4 在线答题

- 用户进入任务页面答题
- 分页或分组展示题目
- 支持中途保存或一次性提交
- 提交后锁定答案
- 记录开始时间、提交时间和作答时长

### 8.4.1 测评时间统计

系统应对用户测评过程中的时间信息进行记录与统计，至少包括：

- 测评开始时间
- 测评提交时间
- 总作答时长

如后续需要更细粒度分析，还可扩展记录：

- 每页停留时间
- 中断次数
- 最后一次保存时间

时间统计可用于：

- 判断任务是否按时完成
- 分析用户作答行为
- 为咨询师复核提供辅助参考
- 支撑后台完成率与效率统计

### 8.5 自动评分与报告生成

- 根据量表规则自动计算结果
- 输出总分、维度分、风险级别
- 生成个人报告
- 支持结果解释与建议模板展示

### 8.5.1 提交后即时出具系统报告

根据当前补充需求，用户完成测评并提交后，系统应立即完成以下动作：

- 自动评分
- 计算总分和维度分
- 判定风险等级
- 生成系统报告
- 将结果反馈给用户或授权查看者

这意味着系统报告应作为测评提交流程的一部分自动生成，而不是依赖后续人工处理。

### 8.5.2 报告类型划分

报告建议划分为两类：

- 系统自动报告
- 咨询师补充报告

两类报告的定位不同，应分别建模和展示。

### 8.5.3 系统自动报告

系统自动报告由系统在用户提交答卷后即时生成，建议包括：

- 量表名称
- 测评时间
- 总分
- 各维度得分
- 风险等级
- 系统解释说明
- 系统建议或提示语

系统自动报告的特点：

- 生成快
- 结构统一
- 可用于批量测评场景
- 适合作为初筛结果

### 8.5.4 咨询师补充报告

咨询师补充报告由咨询师在查看系统报告和个体情况后补充形成，建议包括：

- 对系统结果的人工研判
- 对重点维度的专业说明
- 咨询记录摘要
- 后续建议
- 干预计划
- 是否建议复测、转介或结案

咨询师补充报告的特点：

- 由人工填写或编辑
- 可多次补充或更新
- 更适用于个案跟踪与干预场景

除个体补充报告外，咨询师还需要查看群体层面的分析结果，用于整体研判组织或群体状态。

### 8.5.5 报告关系建议

系统设计时建议将“系统自动报告”与“咨询师补充报告”关联到同一份测评结果之下，形成一主多补充的结构。可采用如下关系思路：

- 一次测评提交产生一条测评结果
- 一条测评结果对应一份系统自动报告
- 一条测评结果可对应零到多份咨询师补充报告

这样既能保证自动化初筛效率，也能满足后续人工跟踪需要。

### 8.6 群体统计分析

- 按学院、班级、部门等维度统计
- 查看平均分、分布情况、异常比例
- 生成群体画像
- 支持多次测评横向或纵向对比

### 8.6.1 群体报告

系统需要支持生成群体报告，主要供咨询师、心理老师或相关专业人员查看，用于把握某个班级、学院、部门或群体的整体心理状态。

群体报告建议支持以下分析内容：

- 测评覆盖人数与完成率
- 总分均值、中位数、最高分、最低分
- 各维度均值与分布情况
- 风险等级人数分布
- 高风险、关注对象比例
- 不同组织之间的横向对比
- 同一群体不同时间的纵向变化

### 8.6.2 个人与群体对比

系统需要支持“个人与群体对比”分析，用于辅助咨询师判断个体在所属群体中的相对位置。该能力建议支持：

- 个人总分与群体平均分对比
- 个人各维度得分与群体维度均值对比
- 个人风险等级在群体中的相对分布位置
- 展示个体相对于群体的偏高、偏低或异常维度

### 8.6.3 群体报告的使用对象

群体报告主要面向以下角色开放：

- 咨询师
- 心理老师
- 测评管理员
- 经授权的学校或企业管理人员

其中涉及敏感信息时，应根据权限控制展示粒度。例如：

- 普通管理人员查看群体汇总，不直接查看敏感个体详情
- 咨询师可查看个体与群体结合分析

### 8.6.4 报告展示建议

群体报告和个人对比建议在展示层面支持：

- 图表化展示
- 维度雷达图或柱状图
- 群体分布图
- 个体与群体均值对比图
- 风险分层统计视图

这样更适合咨询师快速理解整体情况与个体差异。

### 8.6.5 数据与图表展示要求

根据当前补充需求，系统报告与统计页面需要具备一定的数据展示和图表展示能力，不能只输出纯文本结论。

建议在个人报告、群体报告和管理统计页面中结合数据指标与图表组件进行表达。

### 8.6.6 建议展示的数据指标

建议系统至少支持展示以下类型的数据指标：

- 测评人数
- 已完成人数
- 未完成人数
- 完成率
- 总分均值
- 各维度均值
- 风险等级人数与占比
- 高风险人数与占比
- 个人得分与群体均值差值
- 不同时间点的变化趋势

### 8.6.7 建议图表类型

结合当前业务场景，建议优先考虑以下图表：

- 柱状图：用于展示维度得分、组织之间对比
- 折线图：用于展示多次测评趋势变化
- 饼图或环形图：用于展示风险等级分布
- 雷达图：用于展示个人各维度与群体维度对比
- 表格：用于展示详细明细和可导出数据

### 8.6.8 图表应用场景

不同图表可分别用于以下场景：

- 个人报告：个人维度雷达图、个人与群体均值对比图
- 群体报告：群体维度柱状图、风险等级分布图、时间趋势图
- 管理后台：首页统计卡片、完成率图表、预警人数趋势图

### 8.6.9 展示设计原则

图表和数据展示应遵循以下原则：

- 优先帮助咨询师和管理员快速理解重点信息
- 图表数量适中，避免页面信息堆叠
- 图表应与文字解释结合展示
- 对敏感数据做权限控制和脱敏处理
- 支持按组织、时间、量表进行筛选

### 8.7 预警识别与干预跟踪

- 根据阈值自动识别高风险用户
- 建立预警名单
- 记录访谈、复测、转介、结案等处理过程
- 跟踪处理状态与时间线

### 8.8 权限控制与日志审计

- 基于角色的权限控制
- 敏感信息访问控制
- 操作日志记录
- 数据导出审计

## 9. 关键业务特性

为了让系统更有项目亮点，当前讨论中已经提炼出以下关键特性：

- 支持多量表组合测评
- 支持群体画像和趋势分析
- 支持匿名与实名两种模式
- 支持高风险分级预警
- 支持干预闭环管理
- 支持复测对比分析

这些特性适合在项目介绍、答辩说明或需求文档中作为亮点展示。

若以快速落地为目标，建议先实现一个简化版本，核心范围如下：

- 管理员创建量表
- 管理员发布测评任务
- 用户在线完成答题
- 系统自动评分
- 生成测评报告
- 后台查看统计结果
- 高风险结果自动标记提醒

该版本已经能够完成系统主价值闭环，适合作为第一阶段开发目标。

## 11. 非功能需求建议

虽然本轮对话尚未深入展开，但结合项目特点，后续建议补充以下非功能需求：

- 数据隐私保护
- 敏感信息脱敏
- 权限隔离
- 操作可追溯
- 结果解释审慎展示
- 避免将测评结果直接表述为医疗诊断结论

尤其在心理测评场景中，系统应强调“测评参考”和“风险提示”属性，而不是替代专业诊断。

## 12. 业务规则与流程补充

### 12.1 测评模式规则

系统需要支持根据业务场景配置测评模式，建议至少考虑以下规则：

- 支持实名测评
- 支持匿名测评
- 匿名测评场景下，个人身份信息展示范围应受限
- 实名测评场景下，可进入个体预警与干预流程

对于高校和企业不同场景，可按任务维度配置匿名或实名，而不是全系统固定一种模式。

### 12.2 重复测评与复测规则

同一用户可能需要多次参与同一量表，因此系统应支持：

- 首次测评
- 复测
- 随访测评

并建议具备以下规则能力：

- 同一量表允许重复作答
- 每次提交形成独立测评记录
- 支持按时间查看历史测评结果
- 支持前后两次或多次测评对比

### 12.3 作答过程规则

测评任务执行过程中，建议支持以下规则配置：

- 是否允许中途保存
- 是否必须一次性提交
- 是否允许超时后提交
- 提交后是否允许撤回或重做
- 是否限制同一任务只能提交一次

这些规则可按任务或量表场景灵活配置。

### 12.4 预警触发规则

预警不应是固定写死逻辑，而应支持基于量表或任务配置触发条件。建议至少支持：

- 按总分区间触发预警
- 按维度分区间触发预警
- 按高危题项答案触发预警
- 按系统综合规则触发关注或高风险标记

### 12.4.1 匿名测评与个体预警边界

为避免业务冲突，匿名测评与个体预警、个体干预之间的边界需要明确：

- 实名测评：可进入个人报告、个体预警、咨询预约、干预跟踪、复测闭环
- 匿名测评：默认仅用于群体统计、群体报告和趋势分析

如确有业务需要，也可支持“受限匿名”模式，但需额外满足身份映射和权限约束。默认建议：

- 匿名测评结果不直接进入个体预警名单
- 匿名测评结果不直接关联个人咨询预约
- 匿名测评主要用于普查、趋势观察和群体画像

### 12.5 咨询师报告规则

咨询师补充报告应支持一定的过程管理能力，建议包括：

- 支持新增补充报告
- 支持编辑补充报告
- 支持保留历史版本或修改记录
- 支持记录报告编写时间和编写人

### 12.6 预警与干预闭环

预警结果产生后，系统需要形成闭环处理流程，而不是停留在结果展示层面。建议流程包括：

1. 系统识别高风险或关注对象
2. 进入预警名单
3. 指派咨询师或相关负责人跟进
4. 记录访谈、咨询、转介或复测情况
5. 更新处理状态
6. 最终结案或继续跟踪

### 12.6.1 预警接单与升级机制

为了让预警真正闭环，系统需要补充“谁来接、多久处理、超时怎么办”的规则。建议至少支持：

- 预警记录创建后指定责任人或责任角色
- 责任人可为咨询师、心理老师或指定管理员
- 预警记录应包含创建时间、应处理时间、首次响应时间、完成时间
- 超过规定时间未接单或未处理时，系统触发提醒或升级

建议的基本流转为：

1. 系统生成预警记录
2. 自动分配或人工指派责任人
3. 责任人接单
4. 开始跟进处理
5. 完成处理或转交他人
6. 结案或进入持续跟踪

### 12.6.2 超时与升级处理

预警流程建议支持超时控制，至少包括：

- 未接单超时提醒
- 未处理超时提醒
- 超时后升级通知上级或管理员
- 高风险预警优先级高于一般关注项

这样可以避免高风险对象停留在列表中无人处理。

### 12.7 干预状态管理

系统建议对干预流程设置标准状态，例如：

- 待处理
- 跟进中
- 已访谈
- 已转介
- 待复测
- 已结案

这样便于管理员和咨询师统一跟踪处理进度。

### 12.7.1 结案条件建议

为了让干预状态真正闭合，建议补充“结案”判定条件，例如：

- 已完成咨询或访谈记录
- 已形成处理意见
- 必要时已安排复测并获得结果
- 无需继续跟进，或已转介至外部专业机构

系统可要求结案时填写结案说明、结案时间和结案人。

### 12.8 通知与提醒

为了保障测评和干预闭环，系统建议支持消息通知或提醒能力，包括：

- 测评任务下发提醒
- 截止前提醒
- 逾期未完成提醒
- 复测提醒
- 预警提醒

通知可根据终端形态扩展为站内消息、短信、邮件、微信消息或小程序订阅消息。

### 12.9 咨询预约功能

系统建议提供基于咨询师时间安排的预约功能，用于让被测者或相关管理人员按可用时段发起咨询预约。

该功能既可作为独立服务能力，也可与预警处理、个体跟踪和复测流程联动。

### 12.10 咨询师排班与可预约时间

咨询预约功能应以咨询师时间安排为基础，建议支持：

- 配置咨询师可预约时间段
- 配置每个时间段可预约名额
- 配置停约时间、请假时间或不可预约时间
- 支持按日期查看咨询师日程

### 12.11 预约流程建议

建议预约流程至少包括：

1. 被测者或管理员进入预约入口
2. 查看咨询师可预约时间
3. 选择咨询师与预约时段
4. 提交预约申请
5. 系统生成预约记录
6. 咨询师查看预约安排
7. 咨询完成后记录结果或状态

### 12.11.1 预约与干预记录联动

为了避免预约功能孤立存在，预约完成后应与干预闭环联动，建议支持：

- 预约成功后可关联到具体预警记录或测评结果
- 咨询完成后自动生成或引导填写咨询记录
- 咨询记录可更新干预状态
- 如咨询师判断需要复测，可直接创建复测任务
- 如用户失约，可记录失约原因并支持重新预约

这样可形成“预警 -> 预约 -> 咨询 -> 记录 -> 状态更新 -> 复测/结案”的完整流程。

### 12.12 预约状态建议

预约记录建议支持以下状态：

- 待确认
- 已预约
- 已取消
- 已完成
- 已失约

如后续业务需要，也可扩展“已改期”等状态。

### 12.13 预约与测评业务联动

咨询预约可与心理测评业务形成联动，建议支持：

- 高风险预警对象可被推荐预约咨询
- 咨询师可根据个体测评结果安排预约
- 预约记录可关联具体测评结果或预警记录
- 咨询完成后可建议复测或继续跟进

## 13. 权限、隐私与合规补充

### 13.1 权限粒度建议

不同角色应看到不同粒度的数据，建议至少区分以下访问级别：

- 普通用户：仅查看自己的测评任务、个人报告和历史记录
- 咨询师：查看授权范围内的个体报告、群体报告和干预记录
- 测评管理员：查看任务进度、群体统计和必要的管理信息
- 学校或企业管理人员：以查看群体汇总数据为主
- 系统管理员：负责系统配置与权限控制，不默认拥有全部业务敏感信息查看权

### 13.1.5 关键操作权限矩阵建议

除页面可见范围外，还需要对关键业务动作做更细粒度控制。建议至少明确以下权限边界：

- 被测者：可答题、查看本人报告、发起或查看本人预约
- 咨询师：可查看授权个体报告、填写补充报告、处理预警、记录咨询和干预、管理本人预约
- 测评管理员：可创建量表、发布任务、按组或按个人分配测评、查看群体统计、查看任务完成情况
- 学校或企业管理人员：可查看授权范围内的群体汇总报告，不默认查看个体详细敏感信息
- 系统管理员：可管理账号、组织、角色、权限和系统配置，但不默认参与业务结案判断

建议后续单独输出一份角色权限矩阵表，覆盖：

- 页面权限
- 按钮权限
- 数据范围权限
- 导出权限
- 审核/结案权限

### 13.1.1 登录后按角色进入不同功能界面

根据当前补充需求，系统应在用户登录后根据其角色和权限展示不同的功能范围，而不是所有人进入同一套界面。

建议至少区分以下两类核心入口：

- 被测者入口
- 管理者入口

必要时再细分为咨询师入口、测评管理员入口、系统管理员入口等更具体的工作台。

### 13.1.2 被测者可见范围

被测者登录后应只看到与本人测评相关的有限功能，建议包括：

- 我的测评任务
- 开始答题或继续答题
- 我的历史测评记录
- 系统自动生成的个人报告
- 与本人相关的提醒通知

被测者默认不应看到以下内容：

- 量表管理
- 用户管理
- 群体报告
- 预警名单
- 其他人的测评结果
- 后台统计与系统配置

### 13.1.3 管理者可见范围

管理者登录后应进入后台管理界面，只看到与管理职责相关的功能模块。根据角色不同，可包括：

- 量表管理
- 测评任务管理
- 按组或按个人分配测评
- 测评进度统计
- 群体报告查看
- 预警管理
- 干预跟踪管理
- 用户与组织管理
- 数据导出与统计看板

### 13.1.4 前后端实现建议

为了满足“不同角色看到不同功能”的要求，建议前后端同时控制：

- 前端根据登录角色动态展示菜单、页面入口和按钮权限
- 后端根据角色和权限校验接口访问权限

即使前端隐藏了某些页面，后端仍需进行严格鉴权，避免越权访问。

### 13.2 数据脱敏与敏感信息控制

对于高敏感业务数据，建议支持以下控制：

- 非必要角色不展示个体敏感信息
- 群体报告默认不直接暴露个人身份
- 导出时支持脱敏处理
- 对个人详细报告访问进行日志记录

### 13.3 审计与留痕

系统建议对以下关键行为进行审计留痕：

- 查看个人敏感报告
- 导出数据
- 修改量表规则
- 修改咨询师补充报告
- 修改干预状态

### 13.4 隐私授权与免责声明

系统建议在测评开始前或首次使用时提供：

- 隐私政策说明
- 数据使用说明
- 测评知情同意
- 免责声明

尤其需要明确：

- 测评结果仅作为心理状态参考
- 不等同于医学诊断结论
- 高风险结果建议结合人工咨询与专业干预

## 14. 数据展示、导出与运营补充

### 14.1 导出能力

系统建议支持以下导出能力：

- 导出测评明细数据
- 导出群体统计报表
- 导出个人报告
- 导出群体报告

导出格式可优先考虑：

- Excel
- PDF

### 14.2 筛选与检索能力

统计分析和报告页面建议支持多条件筛选，例如：

- 按量表筛选
- 按组织筛选
- 按时间范围筛选
- 按风险等级筛选
- 按任务状态筛选

### 14.3 首页统计看板

系统建议建设首页统计看板，用于快速掌握平台运行状态。可考虑展示：

- 总测评人数
- 当前任务数
- 已完成率
- 高风险人数
- 待处理预警数
- 近期测评趋势
- 近期预警趋势

### 14.4 数据留存与归档

后续若进入正式业务环境，建议补充以下数据治理要求：

- 测评数据留存周期
- 历史数据归档策略
- 报告数据保存周期
- 审计日志保存周期
- 数据删除与恢复策略

## 15. 技术实现约束补充

### 15.1 用户管理基础

用户管理基于 `auth-starter` 基础工程实现，当前已确认其具备如下基础模型：

- 用户：`sys_user`
- 认证信息：`sys_auth`
- 角色与权限：`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`
- 组织能力：`sys_tenant`、`sys_group`
- 审计能力：`sys_login_log`、`sys_security_event`

这意味着本项目可以直接沿用其：

- 认证接口
- 授权模型
- 用户角色管理
- 组织归属管理
- 安全审计模型

### 15.2 本项目建议新增的业务实体

为了适配心理测评系统，后续数据库设计时建议在业务库或业务模块中新增与心理业务相关的实体，例如：

- 测评结果表

其中，用户相关的业务扩展实体应与 `auth-starter` 的 `sys_user` 主键建立关联关系。

在当前需求补充后，建议新增或重点设计的业务实体还包括：

- 预警处理记录表

### 15.3 前后端分层实现

根据当前补充需求，系统需要采用前后端分离思路实现，以便同时支持管理后台、移动端页面和微信小程序。

建议分层如下：

- 后端：负责认证集成、业务规则、量表管理、测评任务、答卷提交、自动评分、报告生成、统计分析、预警与干预跟踪
- 前端管理端：负责管理员、咨询师、心理老师等角色的后台操作与报表查看
- 前端用户端：负责学生或员工进行测评、查看个人报告、接收通知和复测提醒

### 15.4 终端支持要求

系统终端应至少覆盖以下使用场景：

- PC Web 管理端
- 手机 H5 页面
- 微信小程序

不同终端的主要定位建议如下：

- PC Web：适合管理员、咨询师进行任务管理、量表管理、群体报告查看和干预记录
- 手机 H5：适合用户快速完成测评、查看结果、接收提醒
- 微信小程序：适合高校或企业在微信生态内快速触达用户，完成测评和查看个人报告

### 15.5 微信小程序支持说明

微信小程序可作为用户测评入口之一，建议承载以下能力：

- 用户登录或身份绑定
- 查看待完成测评任务
- 在线答题
- 提交后查看系统自动报告
- 查看历史测评记录
- 接收复测提醒或通知

若后续需要更深的微信集成，还可扩展：

- 模板消息或订阅消息提醒
- 与企业微信或校园通知能力结合

### 15.6 前端适配要求

由于需要支持手机和微信小程序，前端设计应满足：

- 页面布局适配移动端尺寸

- 图表在移动端可简化展示
- 关键功能在小程序中具备可用性
- 不同终端尽量复用统一后端接口

### 15.7 后端接口要求

- 统一认证与授权机制
- 统一业务 API
- 明确区分管理端与用户端权限
- 报告、统计、任务、量表等核心能力服务化
- 为移动端和小程序保留轻量化返回结构
